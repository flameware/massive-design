# 한국어 글쓰기 규칙

DS를 쓰는 앱 개발자가 읽는 한국어 글을 쓰거나 고칠 때 이 문서를 먼저 읽는다. 결정의 출처는 [#425](https://github.com/flameware/massive-design/issues/425)이고, 기준 예시는 메인테이너가 승인한 `Foundations/브랜드 색 입히기` 페이지다.

## 대상

- Storybook MDX 문서
- 루트 README(영어 한 줄 요약은 대시 금지의 예외다)
- 패키지 README(`@flameware/tokens`, `@flameware/ui`, `@flameware/storybook`)
- 앱 온보딩 가이드
- 공개 API가 내는 에러 메시지

ADR, 이슈, `docs/handoff/`, `CONTEXT.md` 정의문, 커밋 메시지는 대상이 아니다. 독자가 메인테이너와 에이전트인 내부 글이고, 용어집 어휘를 그대로 쓴다.

## 독자

처음 이 DS를 붙이는 앱 개발자다. 저장소의 이슈, ADR, 내부 스크립트, 사용 중인 앱 이름을 모른다고 가정한다. 첫 문장에서 "이 페이지가 무엇을 해결하는가"를 알 수 있어야 한다.

루트 README의 1순위 독자는 레포를 처음 연 방문자다. 설치와 API는 링크로 넘기고, 문체와 금지 패턴은 그대로 따른다.

## 페이지 뼈대

1. **한 줄 요약**: 무엇을 해결하는지. 가상 앱 이야기나 도입 서사로 시작하지 않는다.
2. **사용법**: 설치, 호출, 연결 순서. 복사해서 바로 쓸 수 있게 쓴다.
3. **주의할 점**: 에러, 제약, 헷갈리기 쉬운 경우. 제목은 독자가 겪는 상황으로 쓴다.
4. **배경**: 설계 이유. 3~4문장 이하로 쓰고 맨 아래에 둔다. 더 길면 ADR 링크로 넘긴다.

컴포넌트 페이지에서는 "언제 쓰는가 / 언제 쓰지 않는가", 변형, 상태, props 표가 사용법과 주의할 점 자리에 온다. 순서 원칙은 같다.

## 문체

- **해요체**로 쓴다. 코드 주석 속 짧은 안내도 해요체다(`/* 반드시 tokens.css 다음에 둬요 */`).
- 한 문장에는 한 가지만 말한다. 길어지면 문장을 나눈다.
- 코드 식별자(`createBrandOverride`, `accent`, `fg.on-solid`)는 원어 그대로, 백틱으로 감싼다.
- 개념어는 사전 없이 이해할 수 있는 말로 푼다. 용어집 용어를 꼭 써야 하면 처음 나올 때 풀어 쓴다. 예: "12단계 배열(램프)".
- 이슈 번호, 내부 스크립트명(`tokens:contrast`), 사용 중인 앱 이름은 사용법 본문에 쓰지 않는다. 필요하면 배경 절에만 둔다. 사용자가 실제로 실행하는 명령은 본문에 둔다.
- "여기서 옮겨 적지 않는다" 같은 내부 편집 방침을 독자에게 말하지 않는다. 링크만 둔다.

## 단어 표현표

용어집 항목의 `_문서에서는_` 줄이 같은 내용을 담는다. 둘이 어긋나면 용어집을 따르고 이 표를 고친다.

| 내부 표현 | 문서에서 쓸 표현 |
| --- | --- |
| 소비처 | DS를 쓰는 앱. 문맥이 분명하면 앱 |
| 자리 | 곳, 경우, 위치로 풀거나 뺀다 |
| 계약 | 지원 범위, 보장하는 동작, 규칙 |
| 게이트 | 검사 |
| 축 | 옵션. 해당 prop 이름을 함께 적는다(예: `size` 옵션) |
| 표면 | 영역, 카드, 패널처럼 구체적인 말 |
| ~가 진다, 몫, 쥔다 | ~가 담당해요, ~가 처리해요 |
| 던진다 | 에러가 나요(`throw`는 코드 블록에서만) |
| 앉는다, 산다 | 들어가요, 있어요 |
| 열지 않았다, 닫는다(범위 결정) | 지원하지 않아요, 제공하지 않아요 |
| 어휘, 정본 | 이름, 공식 이름 |
| 키 컬러 | 기준 색. brand 패밀리에서는 브랜드 색 |

## 금지 패턴

- **본문의 대시(" — ")**. 문장을 둘로 나누거나 괄호, 쉼표를 쓴다. 코드 블록 안은 예외다.
- **"왜 ~인가" 제목**. 제목은 주제나 독자가 겪는 상황으로 쓴다.
- **"X가 아니라 Y다" 대비 단정문**. 독자가 실제로 헷갈릴 만한 경우에만 쓴다. 예: "`Close`가 아니라 실제 동작 버튼에 포커스가 가요"는 괜찮다. 독자가 떠올리지 않은 오해를 먼저 부정하지 않는다.
- **"그래서 ~"로 이어 가는 논증체**. 결론만 말하고, 이유는 필요하면 배경 절에 쓴다.
- **굵은 글씨 남용**. 한 문단에 하나 이하로 쓴다.

## 전후 비교

`Foundations/브랜드 색 입히기` 재작성에서 뽑았다.

**도입 서사를 한 줄 요약으로**

> 전: 두 번째 소비처 숲마루는 자기 브랜드(forest 녹색)로 DS를 쓰고 싶어했다. DS는 `brand` 패밀리 하나를 갖고, 지금 기본값은 `#0f5fed`다.
>
> 후: 브랜드 색 하나를 넘기면 DS의 강조색(`accent`)이 모두 그 색으로 바뀌어요. … 아무것도 하지 않으면 DS 기본 브랜드 색(`#0f5fed`)이 그대로 쓰여요.

**대비 단정문 제목을 상황 제목으로**

> 전: ## 대비 게이트 — 에러다, 경고가 아니다
>
> 후: ### 너무 밝은 색은 에러가 나요

**"왜 ~인가" 제목을 제약과 배경으로 나누기**

> 전: ## 왜 키가 하나뿐인가 / 키 컬러는 모드별이 아니라 **하나다.** DS의 5패밀리와 같은 규약이다 — 키 컬러는 램프의 step 9에 그대로 앉고, …
>
> 후: ### 모드마다 다른 색은 넘길 수 없어요 / 브랜드 색은 하나만 받아요. … (이유는 배경 절로 옮긴다)

**전체를 먼저 말하고, 그중 어디인지 말하기**

> 전: DS의 색은 한 색에서 만든 12단계 배열(램프)이고, 넘긴 브랜드 색은 9단계에 그대로 들어가요. 9단계는 라이트와 다크 모드가 같은 값을 쓰는 유일한 단계라서 브랜드 색을 하나만 받아요.
>
> 후: DS는 브랜드 색 하나로 라이트 모드용과 다크 모드용 12단계 색 배열(램프)을 각각 만들어요. 넘긴 색은 두 배열 모두 9단계에 그대로 들어가서, 9단계는 어느 모드에서나 같은 색이에요. 모드마다 다른 색을 받으면 이 규칙을 지킬 수 없어서 브랜드 색은 하나만 받아요.

무엇을 만드는지 먼저 말해야 "9단계"가 어디인지 보인다. 다음 문장이 기대는 사실(램프가 모드마다 따로 만들어진다)은 앞 문장에 적는다. 이유는 건너뛰지 않고 한 단계씩 잇는다. 독자에게 필요 없는 사실("유일한 단계")은 뺀다.

**번역투 추상어를 구체적인 이유로**

> 전: `brand`는 DS의 접근성 계약을 대신 지고 있는 자리라 게이트가 통과를 강제한다.
>
> 후: 대비 검사를 `createBrandOverride`에서만 강제하는 이유는 DS 컴포넌트 전체가 이 색을 버튼, 링크, 포커스 링에 쓰기 때문이에요.

**결과만 말하던 문장에 독자가 할 일 더하기**

> 전: 못 넘으면 던진다
>
> 후: 위 예시는 라이트 모드에서 흰 글자와 브랜드 색의 대비가 1.92:1이라 기준인 4.5:1보다 낮다는 뜻이에요. 브랜드 색을 조금 어둡게 조정한 뒤 다시 실행해 보세요.

**내부 편집 방침은 빼고 링크만**

> 전: 전체 API와 표는 README에 있다 — 수가 한 곳에만 살도록 여기서 옮겨 적지 않는다.
>
> 후: 전체 API는 `@flameware/tokens` README에 있어요.

## PR에서 확인하기

코드 블록과 백틱 안을 뺀 본문에서 금지 표현을 센다. 대상 파일에서 0건이어야 하고, 결과를 PR 설명에 붙인다.

```sh
awk 'FNR==1{c=0} /^```/{c=!c; next} !c{gsub(/`[^`]*`/,""); print FILENAME":"FNR": "$0}' <파일…> \
  | grep -E ' — |^[^:]+:[0-9]+: #+ 왜 |계약|게이트|소비처|자리|표면|진다|쥔다|쥐고|던진다|앉는다|앉고|살도록|몫'
```

`grep`이 잡은 줄이 규칙 위반이 아닐 수도 있다(예: "만들어진다"의 "진다"). 그런 줄은 PR 설명에 이유와 함께 적는다. 대비 단정문, 논증체, 문장 길이는 기계로 못 세므로 사람이 읽고 판단한다.

PR 설명에는 전후 비교 3~5개도 붙인다. 메인테이너는 배포된 Storybook에서 읽고 판단한다.
